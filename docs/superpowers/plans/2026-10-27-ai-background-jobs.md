# AI Background Jobs Implementation Plan

**Goal:** Accept AI work quickly, execute durably in background, and notify authenticated frontend sessions without losing results or overwriting edits.

**Architecture:** NestJS + BullMQ/Redis for execution, PostgreSQL for job inputs/status/results and a transactional dispatch outbox, authenticated SSE for notifications with REST reconciliation and polling fallback. Initial deployment runs one BullMQ consumer in the API process (concurrency 1), preserving the current ChatGPT token store's single-process refresh lock. Browser disconnection never cancels an accepted job.

**Tech Stack:** Existing Next.js, NestJS, TypeORM/PostgreSQL; add compatible @nestjs/bullmq, bullmq and Redis. Verify dependency peer compatibility before choosing versions.

## Scope and decisions

Phase 1 covers all five existing note AI actions. Phase 2 extends to CV/JD imports after file inputs and draft results have durable storage. Existing import drafts are an in-memory Map and cannot be treated as durable queue results. Do not add WebSocket or browser Web Push initially.

HTTP acceptance is not inference completion. Target POST acceptance p95 <500ms under normal local load; measure queue wait, inference and completion separately. Provider latency is not reduced by introducing a queue.

## API contract

POST /notes/:id/ai-jobs accepts the existing RunAiDto, with an Idempotency-Key header generated by the browser for one logical submission. Scope uniqueness to authenticated owner; same key/different payload returns 409, same key/same payload returns the existing job. Validate note existence/access, action, connection and outstanding-job limits without invoking the model. Persist immutable note/topic/existing-stem snapshot, note revision/hash, selected provider/model, prompt version and rendered instructions; never persist OAuth tokens or API keys in queue data.

Create ai_jobs and ai_job_dispatch outbox together in a PostgreSQL transaction. Return 202 only after durable commit; include Location /ai-jobs/{id}, jobId, status=queued, noteId, action and timestamps. Queued includes pending dispatch; Redis outages leave accepted work pending for recovery, with an explicit visible delayed-queue state after threshold. Database failure returns 503, never a fake job ID. Admission control returns 429 with Retry-After when the bounded pending quota is exhausted.

GET /ai-jobs/:id returns the authenticated owner's job, stage, timestamps, result summary and safe error; other owners receive 404. GET /ai-jobs?status=active and recent completed jobs supports reload recovery. GET /ai-jobs/:id/result returns a typed result only after success, 409 if unfinished, 410 after documented expiry. No raw provider errors/tokens.

GET /ai-jobs/events sends SSE using existing HttpOnly JWT cookie and credentialed CORS. No access token in query parameters. Close on session expiry/logout; reconnect obtains authenticated fresh status. Event payload: {jobId,noteId,action,status,revision,updatedAt}; no full note text. Send typed job.updated events, heartbeat comments, no proxy buffering. Set anti-cache headers and clean up subscriptions on disconnect.

## State and execution

queued -> running -> succeeded
running -> retrying -> queued/running; terminal failed.

Stages are qualitative: waiting, generating, validating, saving. Do not display fabricated percentages or queue ETA. One transient retry at most, exponential backoff with jitter and Retry-After when available; distinguish plan quota exhaustion/auth/config/validation failures (no auto retry) from eligible network/5xx/transient rate-limit failures. Provider abort timeout starts during execution; also enforce a maximum total job lifetime (initial configurable 5 minutes), including retry and wait. Jobs expiring before execution never call AI. Do not add a second competing retry loop inside LlmClient.

Outbox dispatcher sends only {jobId} to BullMQ with deterministic UUID jobId and marks dispatch after Redis acknowledges. Retry dispatch on restart/outage; reconcile non-terminal durable jobs and queue entries. Redis AOF persistence, named volume, maxmemory-policy=noeviction, internal-only port and readiness check. Retain queue entries for an agreed window while PostgreSQL remains the source of truth.

Refactor AiService.run into generation/validation that accepts the immutable snapshot and a finalizer. Reuse current LlmClient, shared Vietnamese style and ChatGPT stream terminal validation. Resolve current owner credentials at execution time; never fall back to server API keys. Revoked connection causes a safe terminal/reconnect-required state. Capture connection identity/generation at admission and reject a changed/disconnected identity at execution; retain request ownership.

Persist valid model output before side effects. Question writes and job success/result commit in one DB transaction, locked by job row, with job-linked uniqueness. Re-delivered BullMQ jobs return persisted terminal results rather than invoking AI again. A crash after provider completion but before output persistence can still cause another model call; do not promise exactly-once inference or billing.

Text actions store preview results and never automatically update notes. Question generation preserves its current behavior of persisting new questions, but does not replace note text. Missing/deleted notes fail clearly. Compare source revision/hash before applying text results; surface 409 conflict and keep preview for manual review. User's current unsaved FE draft must also be checked before application.

## Notifications and frontend UX

One AiJobsProvider inside AppWorkspace owns a single EventSource per signed-in app tab, a job map and a small persistent in-app job history; reconnect/new mount subscribes then fetches active/recent jobs, merging by monotonic revision. SSE is a wakeup signal, not the only delivery guarantee. Refresh on reconnect and window focus; while SSE is unavailable, poll active jobs with jitter/backoff (initial 3s, max15s) and stop for terminal jobs/hidden tab/logout. Periodic slow reconciliation while connected protects against missed event delivery. Don't use a separate SSE stream per job.

Submitting creates a local submitting state, then 202 shows 'Đã tiếp nhận — đang chờ xử lý'. Disable duplicate submission for that note/action while active; backend idempotency remains authoritative. Allow navigation and editing, retain pending status globally. Job finishes on active note: show a quiet completion message and an explicit 'Xem kết quả' action; elsewhere show toast 'AI đã xử lý xong [ghi chú]' with 'Mở kết quả'. Don't auto-navigate, open a modal or replace editor content. Failed job displays a friendly reason and an explicit retry with a new idempotency key. Toasts deduplicate by jobId/revision and are not the result store. Refresh only question data when new questions complete; preserve title/body/topic draft.

SSE works while the page is open. Closed-tab notifications need a later optional Web Push + Service Worker and explicit user permission, not part of version 1. WebSocket becomes useful only if true bidirectional interaction is required; completion events alone don't justify it.

## Acceptance scenarios

- A slow model doesn't keep the submit request open; 202 returns after durable acceptance.
- Navigating away or reloading doesn't lose accepted jobs or completed results.
- Completion reaches active tabs promptly via SSE; reconnect/polling recovers missed notifications.
- No other user's job, result or notification is accessible.
- A replay/retry produces only one committed set of questions; edited note text is never silently overwritten.
- Redis/API restarts and transient provider failures resolve to visible queued/retrying/terminal states, with no permanently orphaned pending UI.

Sources: https://docs.nestjs.com/techniques/queues ; https://docs.nestjs.com/techniques/server-sent-events ; https://docs.bullmq.io/patterns/idempotent-jobs .

## Implementation record

Implemented note AI jobs and the CV/JD extension. The API runs a BullMQ consumer in the same process; PostgreSQL job/outbox and owner-scoped document drafts survive restarts. Redis is internal-only with AOF persistence. Source previews apply with a content-hash conflict check. The API Docker runtime is Node 24 for NestJS 12/Jest ESM compatibility.

Verification includes 7 PostgreSQL/Redis integration cases in a disposable separate database (mocked model calls), owner-isolated SSE and JWT-expiry unit tests, frontend completion/idempotency/reordered-event tests, and the existing suites. Operational details and the exact retention/concurrency limits are in docs/ai-background-jobs.md.
